Spec: decide with the owner which keystone yields (heavy-lift count in long-course build weeks, a distance-aware single weekend keystone, or an alternating long-run / long-ride week) before touching Tier-0 rows. - [ ] **`TASK-058` (`workouts`):** **Walk-Jog (Run/Walk) Re-Entry Workouts** — `EXP-008`: `CURRENT_ATHLETE` is limited by running ACWR / the 75 strain cap, and the shortest candidate run was 30 min. `TASK-051` added continuous 15 / 20 / 25 min Z1 runs (single-run weeks 22 -> 9 on olympic) but deliberately NOT run/walk rows: the canonical schema (zone minutes, one `mechanical_strain`, `neuromuscular_load`, `axial_load`) has no walk component, and a lower impact load for 1:1 run/walk would be an unmeasured number that loosens the in-model ACWR and strain rows (`GEMINI.md` §2). - [ ] **`TASK-059` (`safety`):** **Brick Run Leg Is Invisible To Run-Load Accounting** — `EXP-008`: `safety_constraints.run_minutes` / `run_strain` count only `sport == "Run"` and lift + run combos; a `Brick` (bike -> run) contributes 0 run minutes, 0 run strain, nothing to the running ACWR row, the weekly run-strain cap, the single-run-share cap or the 48h separation sets, although `calendar.make_allowed` counts it as both a Bike and a Run session for frequency. The 9 authored bricks (`BR1..BR6`, `RUN_TB1/2_BRICK`, `SW_T1_BRICK`) are therefore kept out of `lib_default`; adding even a 45 min bike -> 15 min run brick would give the solver a free run. Spec: add a brick run-leg field (minutes, strain, hard flag) to `WorkoutTable` / `CandidateWorkout`, feed it to the run-minute guard, ACWR, run-share, weekly strain and heavy-run separation rows (as lift + run combos already do via `cardio_*`), test with a synthetic brick; only then add short bricks (45-75 min) to `lib_default`.
- [ ] **`TASK-060` (`perf`):** **Candidate-Set Growth Costs Solve Time** — `EXP-008`: +31 `lib_default` rows (22 endurance, 3 strength, one set of three near-duplicate easy runs) took the `CURRENT_ATHLETE` olympic season from ~33 s to ~101 s (matrix, 8 processes), almost all from two non-heavy lifts whose lift x {Bike, Run} x {10, 20 min} combos multiply the row count; removing them (and 3 unused endurance rows) gave 42 s with identical relaxations. ## Phase 3: Physiology Calibration & Periodization
- [ ] **`TASK-021` (`physiology`):** **Unify ANS Cost, Mechanical Strain, Strength TSS & Banister PMC Math** — Unify the 3 conflicting ANS formulas into the 7-zone `SPEC.md` weight vector $w=(0,0,0.7,1.0,1.4,1.8,3.5)$ with alactic stride exemption and long-duration surcharge; replace stacked-constant mechanical strain with zone-power exponent model $S^{\text{run}}_i = \sum_z t_{i,z} p_z^\beta$ and set-intensity strength strain; assign strength a realistic aerobic TSS (10–20/hr instead of 56 TSS); fix `AthletePhysiologicalState.step_day` (`:1628-1629`) from $\alpha = 2/(N+1)$ to exact Banister decay $\alpha = 1 - e^{-1/\tau}$ ($\tau=42, 7$) and reconcile strength TSS in `total_ctl` vs `metabolic_fitness_state`; recalibrate 48h caps to match.
- [ ] **`TASK-050` (`physiology`):** **Ironman Build Weeks Bound By The 48h ANS Cap; Distance-Aware Anchors** — `TASK-040` (ablation on reference Ironman, charter caps 295 / 260 / 700): build weeks 14, 15, 18, 19 solve 572 vs targets 636-711 with 48h ANS at 690 of 700 (48h TSS only 272-294, strain 185). Raising only 48h TSS (420) or the CTL ramp (20) changes nothing; raising TSS 420 + strain 380 + ANS 1000 reaches 619 and picks 210 min rides, so the ANS cap is the binder and it cannot be loosened (`GEMINI.md` §2). `C_ans = sum T_z e^(0.65 (z-1))` charges a Z2 minute 1.9x a Z1 minute, so a 240 min Z1/Z2 ride costs 372 ANS. Owner decision: keep the Ironman targets unreachable (reported by the season diagnosis), or revisit the ANS weighting of low-intensity long sessions with `TASK-021`. Also open: distance-aware anchors (the 180 min ride `BIKE_DUR_OUT_DEF` / 75 min run `RUN_AE2_LONG` are mandatory in every build week for every distance; an IM long-ride anchor of 240 would add ~60 TSS to a weekend pair already at 260 of the 295 48h cap), to be done via `RACE_DEMANDS`-style config only if the ANS decision allows it. **Deferred by owner to `TASK-021` (ANS weighting of Z1/Z2 long sessions; keep the 700 cap): the ANS-cap decision is part of the TASK-021 re-weighting.**
